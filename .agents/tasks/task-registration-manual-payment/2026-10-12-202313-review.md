# Customer registration fix and Midtrans-free manual payment with owner verification

Three coordinated changes to the kost app: registration is hardened so a new customer always gets `role='customer'` and the shared login/register Blade form posts to `/register` server-side instead of relying on JS; the Midtrans/QR checkout is replaced with a manual flow offering `bank_transfer` (dummy bank details from a new `config/payment.php`, proof image uploaded to the public disk) and `on_site`, both landing the booking in status `review` and writing a `Payment` row; and the Filament Bookings admin gains a payment-method column, the existing proof image, and Approve/Reject record actions that move the booking to `active`/`pending` and the payment to `success`/`failed`. No DB_* keys changed, `canAccessPanel` still gates owner/staff, and the booking CHECK constraint reuses `review`/`pending` without a new status.

Watch for: the Approve/Reject admin actions are not exercised by any automated test — the feature test replicates the update logic inline rather than invoking the Filament actions, so a regression in the action closures would pass CI (confirmed). The bundled Filament admin theme, `Color::Stone` gray palette, and the `ExampleTest` RefreshDatabase change are unrelated to the task (confirmed).

**Verdict**: APPROVED

## High-level view

Registration now sets `role` in three places — the controller `User::create`, a model `$attributes` default, and the pre-existing DB default — so a null role is impossible by construction. The shared login/register form resolves its action from the `$mode` variable server-side, closing the JS-dependent failure where register fields silently posted to `/login`.

The manual payment path reads dummy bank details from `config('payment.bank')` with hardcoded fallbacks, so it works even without the `KOST_BANK_*` env keys. Checkout validates exactly `bank_transfer|on_site`; bank transfer requires an image proof stored on the public disk, on-site requires nothing. Both methods create a `pending` Payment and set the booking to `review`. Midtrans is gone from this path — the package stays installed but unreferenced.

Owner verification lives in the inline `BookingResource` table and actions. Approve and Reject each run in a DB transaction and are visible only for `review` bookings. Approve activates the booking, occupies the room, and marks the latest Payment `success` with `verified_at`; Reject returns the booking to `pending` (never active) and marks the Payment `failed` with an optional reason in `notes`. The room is deliberately left untouched on reject.

The booking status CHECK constraint reuses `review` and `pending`; on pgsql the migration chain re-adds the constraint with `review` included, and the base create-table enum now lists `review` so the sqlite test DB accepts it. Approve/Reject are only covered by inline-replicated test logic, not by invoking the actions themselves.

### Role and panel access

`role` is set in three independent layers: `RegisteredUserController@store` passes `'role' => 'customer'`, `User` carries `protected $attributes = ['role' => 'customer']`, and the DB column default remains. The controller omission was the real gap the feature targeted. `canAccessPanel` is unchanged and gates on `in_array($this->role, ['owner','staff'])`, so a registered `customer` cannot reach `/admin`. Verified seeded `owner@arca.com` → `owner` and `alvin@gmail.com` → `customer`.

The shared `login-page.blade.php` form action changed from a hardcoded `url('/login')` to `($mode ?? 'login') === 'register' ? url('/register') : url('/login')`. The register-only fields are CSS-hidden rather than removed from the DOM, so they submit in register mode even if JS does not run — closing the previously flagged failure where register fields silently posted to `/login`.

### Manual payment: config-backed bank details, two methods, no Midtrans

```
checkout POST
  payment_method in: bank_transfer | on_site
      │
      ├─ bank_transfer → validate image (jpg/jpeg/png ≤4MB, required)
      │                  delete prior proof → store proofs/ on public disk
      │                  booking.proof_of_payment = path
      │
      └─ on_site      → no upload
      │
      ▼
  booking.status = 'review'
  Payment::create(method, amount=total_price, status='pending')
```

`config/payment.php` returns `bank.name/account_number/account_holder` from `KOST_BANK_*` env with dummy fallbacks, so the pay page renders account digits even with no env entries — confirmed `config('payment.bank.account_number')` returns `1234567890` after a fresh seed. `BookingController@pay` dropped the `SimpleSoftwareIO\QrCode` import and QR generation; the owner-only 403 guard is preserved. The Midtrans package stays installed but is unreferenced on this path.

`processCheckout` creates a new `Payment` row on each submit and, for bank transfer, deletes the prior proof before storing the new one. A customer who resubmits after a reject (booking back to `pending`) accumulates multiple Payment rows; the admin actions operate on `payments()->latest()->first()`, so the newest attempt wins. The Payment history is append-only by design — not a defect, but worth knowing when auditing payments.

### Owner verification actions

Approve and Reject are both `visible(fn => $record->status === 'review')` and wrapped in `DB::transaction`. Approve sets booking `active`, room `occupied` (guarded by `if ($record->room)`), and the latest Payment `success` + `verified_at=now()`. Reject sets booking `pending`, latest Payment `failed`, and `notes` from the nullable `reason` textarea, and deliberately does not touch the room — the test asserts the room is not `occupied` after a reject. Both target statuses and the pre-checkout `review` are inside the pgsql CHECK constraint, so no violation is possible.

The payment-method column reads `getStateUsing(fn => $record->latestPayment?->payment_method)` with friendly labels and keeps the proof `ImageColumn` on the `public` disk. Note `latestPayment()` is `hasOne(...)->latestOfMany()` while the action bodies read `payments()->latest()->first()` — two different expressions of "latest payment" that agree in practice.

### Status constraint reuses `review`/`pending` across both drivers

The base `create_bookings_table` enum gained `review`, which is what lets the sqlite test DB accept an update to `review` (sqlite renders `enum` as a CHECK constraint and the pgsql-only ALTER migrations self-skip there). On pgsql the migration chain ends at `2026_06_15_000002` with `CHECK (status IN pending, review, active, cancelled, completed)`, and `2026_05_20_085218` was also guarded with a `DB::getDriverName() !== 'pgsql'` early return. No new status string was introduced; `review` for awaiting-verification and `pending` for rejected are reused as the task requires. `migrate:fresh --seed` runs clean on PostgreSQL end to end.

### Test coverage

`ManualPaymentFlowTest` (6 tests, 32 assertions, green) covers: register → `role='customer'` + `/dashboard` 200; pay page renders the dummy account number from config; bank-transfer checkout with a faked image stores the proof on the public disk, sets `review`, and creates a `(bank_transfer, pending)` Payment; on-site checkout sets `review` and creates `(on_site, pending)` with no proof; and the approve/reject outcomes.

Not tested: the actual Filament Approve/Reject action closures. The approve and reject tests re-implement the update logic inline (`$booking->update(['status'=>'active'])`, etc.) rather than invoking the real action via Filament/Livewire. The acceptance outcomes are asserted, but the transaction wrapping, the `if ($record->room)` guard, the `->latest()->first()` payment selection, and the notification calls inside the real closures are never run. A regression there would be invisible to CI. The feature spec explicitly permitted replication, so this is an accepted gap rather than a spec violation.

The full suite is `30 passed, 1 risky`. The risky one is `ExampleTest` hitting `/` and asserting 200 while the route redirects; this test was flipped to `RefreshDatabase` in this diff but the assertion itself is stock Laravel scaffolding unrelated to the task, so it neither blocks nor regresses the feature.

### Unrelated changes in the diff

`AdminPanelProvider` gained a `Color::Stone` gray palette and a `renderHook(HEAD_END, ...)` injecting `public/css/admin-theme.css`, and `ExampleTest` was switched to `RefreshDatabase`. None of these relate to registration, manual payment, or owner verification. They are low-risk and verified green, but they widen the review surface and would be cleaner as a separate change.
